# AI Concept Visualizer

バイブコーディングの学習中に出会った用語を 1 つ受け取り、図解 HTML を生成する。
説明文ではなく図で理解させることを最優先にする。

## 依存

- `references/model-answer.html` / `references/model-answer-newspaper.html` — 模範回答。品質基準・デザイン・情報量はここから読み取る
- `references/base.html` / `references/base-newspaper.html` — 額縁テンプレート
- `scripts/verify-diagram.mjs` — レイアウト崩れの検証スクリプト
- `references/playwright-setup-guide.md` — Playwright 未導入時の案内

## ワークフロー

- [ ] Step 1: デザインを決める
- [ ] Step 2: 模範回答とテンプレートを読む
- [ ] Step 3: ウェブで調べる
- [ ] Step 4: 9 セクションで書く
- [ ] Step 5: ファイルを作る
- [ ] Step 6: 中身を確認する
- [ ] Step 7: 見た目を検証する
- [ ] Step 8: 報告する

### Step 1: デザインを決める

- 「ノーマルと新聞風、どちらのデザインにしますか」と 1 問だけ聞く
- 依頼文にすでに指定がある場合（「新聞風で」など）は聞かずにそれに従う

| デザイン | 模範回答 | 額縁テンプレート | 特徴 |
|---|---|---|---|
| ノーマル | `references/model-answer.html` | `references/base.html` | 白地・角丸カード・Lucide アイコン |
| 新聞風 | `references/model-answer-newspaper.html` | `references/base-newspaper.html` | 紙色・明朝・罫線・図番号つきキャプション。アイコンは使わない |

### Step 2: 模範回答とテンプレートを読む

- 選んだデザインの模範回答を読み、品質基準・デザイン・1 セクションあたりの情報量を把握する
- 選んだデザインの額縁テンプレートを読み、`<!-- TITLE -->` `<!-- DESCRIPTION -->` `<!-- CONTENT_START -->`〜`<!-- CONTENT_END -->` の位置を把握する

### Step 3: ウェブで調べる

- ウェブ検索を 2〜3 回行う。観点は「正確な定義」「最新動向」「制作シーンでの実例」
- 公式ドキュメント・一次情報を優先する。個人記事は一次情報が無い論点に限る
- 採用した事実の出典 URL と調査日を控えておく（Step 4 で本文に添える）
- コマンド・パッケージ名・オプションを載せるときは、現在も有効かをこの段階で確認する

### Step 4: 9 セクションで書く

- 下記「図解の構成」の表と「セクション 5 の要件」に沿って、セクションごとに図を先に設計してから文章を当てる
- 各セクションは「書き方」のルールに従う

### Step 5: ファイルを作る

- `output/` ディレクトリが無ければ作成する
- 選んだデザインの額縁テンプレートを、リポジトリ直下の `output/{スラッグ}.html` にコピーする
- `<!-- TITLE -->`（og:title と title の 2 箇所）、`<!-- DESCRIPTION -->`、`<!-- CONTENT_START -->`〜`<!-- CONTENT_END -->` を置換する
- スラッグは短い英単語にする（例: `env-vars`, `git-commit`）

### Step 6: 中身を確認する

書き上げた HTML を自分で読み返し、次の 5 点を確認する。1 つでも引っかかれば直してから次へ進む。

- [ ] 図の中の数値・ラベルと、地の文・キャプションの主張が矛盾していないか
- [ ] 括弧書き解説のない専門用語が残っていないか
- [ ] 画面再現のコマンド・パッケージ名・ファイル名・オプションが、実行して通る内容か
- [ ] 全セクションを通して、同じものを同じ名前で呼んでいるか（図に出ていない登場人物を後から出さない）
- [ ] 知らないと損害・手戻りが出る注意が抜けていないか（安全・費用・本番環境）

### Step 7: 見た目を検証する

- `node .claude/skills/ai-concept-visualizer/scripts/verify-diagram.mjs output/{スラッグ}.html` を実行する
- `RESULT: CLEAN` になるまで修正して再実行する（最大 3 回）
- 依存が無い場合は `references/playwright-setup-guide.md` の手順で導入する
- 最後に 1 回だけ `--screenshot <出力プレフィックス>` でスクショを撮って目視確認し、確認後はスクショを削除する（成果物として残すのは `output/{スラッグ}.html` のみ）

### Step 8: 報告する

完成報告に含める:

- タイトル
- 使ったデザイン（ノーマル / 新聞風）
- 1〜2 文の要約
- 保存先（`output/{スラッグ}.html`）
- 検証結果と残課題
- 主なポイント 3〜5 個

## 図解の構成（順序固定・省略不可）

| # | セクション | 主役の図 |
|---|---|---|
| 1 | ヒーロー＋一言の答え | カテゴリバッジ＋太字1文 |
| 2 | 一枚絵サマリー | 核心の図＋身近な接点ピル（見出しなし） |
| 3 | なぜ必要？ | 「ないとき ✗ / あるとき ✓」左右対比 |
| 4 | どう動く？ | 番号つきステップフロー |
| 5 | 制作シーンで見る | 作業タイムライン＋画面再現 |
| 6 | よくある勘違い | ✗誤解 → ✓正解カード |
| 7 | AIへの伝え方 | 指示例 Before / After |
| 8 | これだけ覚えればOK | 3行まとめ |
| 9 | 次に調べる | 関連語 2〜3 個＋なぜそれか一言 |

### セクション 5 の要件

このスキルの中核。次の 2 つを必ず入れる。

- **作業タイムライン** — バイブコーディングの作業の流れの中で、その用語が登場する瞬間を強調した横並びの図
- **画面再現** — ターミナル / エディタ / チャット / ブラウザのいずれかを Tailwind CSS で再現し、その用語が現れる箇所を指し示す
  - 読者がそのままなぞれる具体値を最低 1 つ、省略せずに載せる（`...` で伏せない）

作っているものが会話からわかればその文脈を使う。わからなければ典型的な場面（Web アプリを作る / エラーが出た / デプロイする）を使う。

## 書き方

- セクション見出しの直後は必ず図。地の文を先に置かない
- 地の文は図の後、最大 3 文
- 図で説明できない内容は載せない。ただし、知らないと損害・手戻りが出る事項（安全・費用・本番環境）は、まず図にする方法を考える。どうしても図にできない場合に限り、短い注記として残す
- 専門用語は初出で括弧書き解説する。判定基準は「バイブコーディングを始めて 3 か月の人が説明できない語はすべて対象」。迷ったら解説する
- 採用した事実の近くに出典リンクを添える。添え方（見た目・文言）は模範回答に倣う
- 変わりうる数値（料金・上限・バージョン）には「◯年◯月時点」を添える
- 日本語で書く
- 読者のレベルに言及しない（「初心者向け」「入門」等のラベルを使わない）

## 禁止事項

- React・shadcn/ui を使わない
- 絵文字を使わない（ノーマルのアイコンは Lucide Icons。新聞風はアイコンを使わず、罫線と図番号で示す）
- インタラクティブ要素・アニメーションを入れない
- 本文に `<style>` タグ・`style` 属性を追加しない（Tailwind クラスで書く。装飾の定義は額縁テンプレート側に入っている）
- `<script>` を追加しない
- テンプレート以外の外部リソースを読み込まない
- テンプレートの額縁構造（`<head>`・CDN・meta）を変更しない
